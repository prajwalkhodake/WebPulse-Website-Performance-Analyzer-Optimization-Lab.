Engineering Rationale & System Architecture

WebPulse is an educational, portfolio-grade developer laboratory designed for static source analysis, interactive dependency modeling, and isolated headless browser performance testing of local, pre-deployment web projects.

Python 3.13 + Flask 3 MySQL + SQLite Dual ORM Cytoscape.js Network Graph Playwright Chromium Sandbox Anti-Zip-Slip Defense

Problem Statement & Engineering Motivation

Traditional web performance diagnostic utilities (such as Google PageSpeed Insights, GTmetrix, or WebPageTest) operate externally across the public internet. Consequently, they require live DNS entries and publicly accessible URLs. This architecture presents severe limitations:

The Pre-Deployment Blindspot

Local projects, student capstones, internal prototypes, and staging applications behind corporate firewalls cannot be evaluated using public cloud audit tools.

Late Defect Discovery

Engineers frequently push code containing render-blocking scripts in <head>, missing responsive viewports, circular imports, uncompressed raster graphics, or broken relative links without knowing until after production deployment.

The WebPulse Solution: WebPulse ingests local website source code archives, validates their safety outside the web root, parses their code structure statically, models their internal dependency topology, and spins up an ephemeral loopback server to execute headless browser tests with the real Navigation Timing API.

WebPulse Terminology & Concepts Glossary

An exhaustive engineering dictionary explaining the core metrics, diagnostic concepts, and algorithms utilized across WebPulse

1. Static Finding (AST & Heuristic Analysis) Code Inspection

A Static Finding is a code-level defect, performance bottleneck, accessibility violation, or antipattern identified by parsing website source files (HTML, CSS, JavaScript, assets) directly on disk without executing the code in a browser engine.

  • Line-Level Evidence: Every finding records the affected file path, exact line number, and raw source snippet demonstrating the violation.
  • Severity Tiers: Critical (functional breakage, missing viewport, render-blocking scripts, broken links), Warning (uncompressed imagery, un-dimensioned images causing layout shifts, duplicate CSS selectors), and Info (development artifacts like console.log, modern WebP/AVIF format recommendations).
  • Confidence & Impact: Findings evaluate how certain the scanner is of the problem and the anticipated magnitude of user experience degradation.
2. Dependency Graph (Cytoscape.js Network) Graph Theory

The Dependency Graph is an interactive topological visualization modeling how every file in the project relates to others. WebPulse traverses the directory structure and constructs directed graph elements (nodes and edges):

  • Nodes: Represent project files. Color-coded by classification: HTML (entry points), CSS (stylesheets), JavaScript (scripts), Images (raster/vector assets), and Broken Missing (files referenced in code that do not exist on disk).
  • Edges: Directed connections indicating dependencies (e.g. index.html → styles.css via <link rel="stylesheet">, or main.js → utils.js via ES module import).
  • Broken 404 Node Detection: When code links to a non-existent asset, WebPulse synthesizes a virtual crimson node in the graph to immediately alert developers to missing files.
3. Controlled Browser Performance Lab (Playwright Runner) Runtime Testing

Unlike static code analysis, the Browser Performance Lab measures real-world execution behavior by launching a headless Chromium browser instance controlled by Playwright.

  • Ephemeral Loopback Server: Untrusted uploaded code is never served on WebPulse's main authenticated web origin. WebPulse spins up a private loopback HTTP server dynamically bound to 127.0.0.1:0 (an OS-assigned random port) and terminates it immediately after testing.
  • Controlled Viewports: Simulates both Desktop (1280x800) and Mobile (390x844 iPhone with touch simulation) device environments.
  • Navigation Timing Extraction: Queries the browser's native window.performance.getEntriesByType('navigation') to extract real, millisecond-accurate metrics without guesswork.
4. Core Web Vitals & Navigation Timings W3C Metrics

Key performance indicators standardized by Google and the W3C to evaluate user-centric perceptual loading speed, visual stability, and responsiveness:

Metric Description Healthy Threshold
TTFB (Time to First Byte) Time from initial HTTP navigation request until the browser receives the very first byte of the HTML response document. < 800 ms
FCP (First Contentful Paint) Timestamp when the browser renders the very first DOM element (text, image, or SVG) on the screen. < 1800 ms
LCP (Largest Contentful Paint) Timestamp when the largest content block (typically a hero banner, video poster, or large heading block) finishes rendering. < 2500 ms
CLS (Cumulative Layout Shift) Score quantifying unexpected layout jumps during page load (e.g. unsized images pushing text downward while loading). < 0.100
Full Load Event Total time required for the HTML document, all external stylesheets, scripts, fonts, and images to complete downloading. < 3000 ms
5. Network Resource Waterfall Network Analysis

The Waterfall Chart is a chronological timeline plotting every network request dispatched by the browser while loading the web page.

  • Serial vs Parallel Execution: Identifies blocking serial request chains (such as CSS @import rules where the browser must download file A before it even learns file B exists).
  • Transfer Footprint: Records exact bytes transferred across HTML, CSS, JavaScript, images, and fonts, pinpointing oversized assets consuming bandwidth.
  • Failed Request Interception: Tracks non-200 HTTP responses (404 Not Found, 500 Server Error) that degrade user experience.
6. Deterministic Multi-Factor Scoring & Recommendations Algorithm

WebPulse intentionally avoids arbitrary or opaque "black-box" scores. All recommendations and overall scores are computed using a mathematical, deterministic formula:

  • Priority Score Formula: Score = Base_Severity (Critical: 40, Warning: 20, Info: 10) + Impact_Weight (High: 30, Medium: 15, Low: 5) + Confidence_Weight (High: 20, Medium: 10, Low: 5) + Magnitude_Bonus.
  • Categorized Action Plans: Recommendations are bucketed into Priority 1 (High, Score ≥ 70), Priority 2 (Medium, Score ≥ 45), and Priority 3 (Low) with step-by-step code remediation instructions.
7. Version Diffing & Regression Analysis Comparative QA

WebPulse tracks releases chronologically (v1.0 Baseline vs v2.0 Optimized) to demonstrate the tangible benefits of optimization interventions:

  • Resolved Findings (Green): Static defects identified in the baseline version that were successfully corrected in the target version.
  • Persistent Findings (Yellow): Unresolved issues that remain present across both versions.
  • New Findings / Regressions (Red): Newly introduced defects or performance regressions that were not present in the baseline release.
  • Metric Deltas: Mathematical difference in score (+pts), transfer size (-KB), FCP/LCP speedups (-ms), and layout stability gains.
8. Anti-Zip-Slip Sandbox & Quarantine Architecture Application Security

WebPulse processes untrusted user-submitted archives with rigorous multi-tier security boundaries:

  • Zip-Slip Path Traversal Protection: Archive entry paths containing ../ traversal sequences, absolute paths (/etc/passwd), or symbolic links are detected and immediately rejected before extraction.
  • Decompression Bomb Mitigation: Enforces strict decompression expansion ratios and ceiling limits (max 50MB uncompressed) to prevent denial-of-service storage exhaustion.
  • Secret & Artifact Scrubbing: Strips sensitive files (such as .env, .git credentials, and OS junk like .DS_Store) during validation.
  • Quarantined Storage: Extracted project files are stored in storage/projects/ outside the Flask static folder so they cannot be accessed directly via URL requests.
